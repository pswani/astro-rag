## 1. Decision

Analysis rests on two things: **facts computed by code** and **text from registered, authentic sources**. An expert reviewer improves what the system knows, but no longer gates it.

| Before | After |
|---|---|
| Every rule is a hand-reviewed rule card; about 1,100–1,400 cards and 90–120 reviewer-hours before the Core release | The large placement families need **no cards**: a computed fact selects the verses written about it, through **typed factor tags** on passages |
| A card is usable only when an expert reviewed it | A card is usable when it passes **automated verification** (`verified`). An expert can promote it to `reviewed` |
| Until a topic's cards were reviewed, the topic was answered `partial` | Every topic is answered from the start; unverifiable items are listed, not hidden |
| Fixtures written per card | Fixtures **generated by the engine** for every verified condition |

Three things do not change, because they never depended on an expert:
1. **Calculation is code.** Positions, lordships and periods are computed, never read from text or a model (OUT-2).
2. **The LLM never decides whether a condition holds for a chart** (APP-1). Applicability is decided by deterministic code from verified predicates, and every decision replays without a model (APP-5).
3. **Every claim cites the verse it rests on** (OUT-1), so the reader can always check the authentic text.

## 2. Three ways a passage is used

| Kind | What it is | Examples | How it reaches an analysis |
|---|---|---|---|
| **Factor passage** | A verse about one chart factor | "If the lord of the 7th is in the 12th…", "Saturn in the 10th…", "Jupiter in Cancer…" | Its verified **factor tag** equals a factor the chart has (§3) |
| **Rule card** | A compound condition: a formation with cancellations, or several factors at once | Gajakesari and its cancellation; Neecha Bhanga; a dasha-lord combination; BNN combinations | Its verified **predicate** is evaluated on the facts (design §10) |
| **Prose** | Text without an extractable condition | General descriptions, commentary, principles | Semantic and lexical search only. Shown as general text and never presented as applying to the chart |

Most of the Core families in KNW-5 are single factors: graha in rashi (108), graha in bhava (108), lord in bhava (144), graha in nakshatra (243), conjunctions (~250), aspects (~70), simple transits (~108). They become factor passages. Cards remain for the compound families: the curated yogas and doshas (20–30), dasha × antardasha combinations that a text states with conditions, conditions inside verses (§4), and BNN combinations (phase 5). That is on the order of 100–300 cards.

## 3. Typed factor tags

### 3.1 Why entity sets are not enough

Retrieval used to filter on entity sets (design §12.3: `grahas ∋ saturn`, `bhavas ∋ 10`). A dry run showed that the set {7th house, 12th house} retrieves both "the 7th lord in the 12th" and "the 12th lord in the 7th" (§11, round 0). Direction and role are part of the factor, so factors are typed.

### 3.2 Factor vocabulary

A closed list, each with typed slots, validated like the predicate DSL:

| Factor | Key example | Computed from |
|---|---|---|
| `graha_in_rashi(graha, rashi)` | `graha_in_rashi:saturn:libra` | `sign` |
| `graha_in_bhava(graha, house, frame)` | `graha_in_bhava:saturn:10:lagna` | `house` |
| `lord_in_bhava(of_house, house, frame)` | `lord_in_bhava:7:12:lagna` | `lord_of` + `house` |
| `graha_in_nakshatra(graha, nakshatra)` | `graha_in_nakshatra:moon:rohini` | `nakshatra` |
| `conjunction(graha, graha)` (unordered) | `conjunction:mars:saturn` | `conjunct_with` |
| `aspect(graha, target)` (ordered; target a graha or a house) | `aspect:jupiter:bhava7:lagna` | `aspects`, `aspects_signs` |
| `graha_dignity(graha, dignity)` | `graha_dignity:jupiter:debilitated` | `dignity` |
| `dasha(system, level, lord[, parent])` | `dasha:vimshottari:AD:venus:saturn` | the period tree |
| `transit_bhava(graha, house, from)` | `transit_bhava:saturn:12:chandra` | transit positions |

The frame defaults to the Lagna when a verse counts houses without a reference point (design §9.6, unchanged).

### 3.3 Matching is set intersection

- **At ingestion**, each passage gets `factors: [{key, status, gates}]` (design §9.7). Only `verified` and `reviewed` keys go into the indexed `factor_keys` payload field.
- **At query time**, a deterministic `FactorIndex` turns the chart's facts into the set of factor keys the chart has. A fact that is `sensitive` or `unknown` gives no key, and is reported as an `unknown` factor instead (APP-2).
- **The factor route** filters on exact `factor_keys`, inside the search (RET-2). "Saturn in the 10th" can no longer return "10th lord in Saturn's sign", because those are different keys (RET-3).
- Each match is recorded as a **FactorMatch**: the fact handles, the passage handle, the key and its tag status. It is a deterministic decision like a rule decision, and it replays without a model.

## 4. Conditions inside verses

Many factor verses add a condition: "…the evil is reduced if a benefic aspects the 7th lord." If the analyst LLM decided whether that holds, it would break APP-1.

- At ingestion, the extractor lists each condition's text span. Where it can, it writes the condition as a predicate, which goes through the same verification (§5).
- At query time, a verified condition is **evaluated** (`true`, `false` or `unknown`). Any other condition is **`unchecked`**.
- The bundle carries every condition with its result. The analyst must present an unchecked condition as conditional ("the text adds that a benefic aspect reduces this; that was not checked"). The evidence checker rejects a claim that asserts a condition's outcome without a decision handle (design §13.3).

## 5. Extraction and verification

One pipeline serves factor tags, in-verse conditions and rule cards.

### 5.1 Extraction

Two independent passes over the verse and its translation, with different prompts, and different models when both are configured (local and API). Each returns a predicate in the allowlisted DSL, or `none` when the text has no extractable condition. Outputs are cached by input hash, so re-running the gates costs nothing.

### 5.2 Gates

| Gate | Check | Catches |
|---|---|---|
| G1 Schema | Valid operators, slot types and factor keys | Malformed or invented operators |
| G2 Agreement | The two passes give the same canonical predicate | One-sided misreadings |
| G3 Mentions | Every graha, sign, nakshatra and house number in the predicate is named in the verse or its translation (alias matcher and ordinals) | Invented entities and numbers |
| G4 Parse | For formulaic phrasings ("the lord of the Nth house is in the Mth house"), a deterministic pattern parse must equal the predicate. It abstains on other phrasings | **Errors both passes share**, such as swapped direction |
| G5 Order | Where the edition's chapter map declares a structure (e.g. a chapter going through each house's lord in each house), the tags must follow that order | Shared errors in structured chapters, including non-formulaic verses |
| G6 Realizable | The engine finds charts where the predicate is true and false (and `unknown` where a sensitive fact is involved). These become the EVAL-4 fixtures | Contradictory or vacuous predicates |
| G7 Back-translation | The predicate is rendered to English by template (deterministic). A third LLM call, given the verse and the rendering, answers faithful / not faithful and quotes the deciding phrase | Lost exceptions, wrong scope, paraphrase drift |

All applicable gates pass → **`verified`**. Any failure → **`queued`**, with the failing gates and a one-line reason.

### 5.3 Statuses

| Status | Meaning | Used in analysis | Label in answers |
|---|---|---|---|
| `draft` | Extracted; gates not yet run | No | — |
| `verified` | All gates passed | Yes | machine-verified |
| `queued` | A gate failed; awaiting a person | No (the verse is still retrievable as prose) | — |
| `operator_verified` | A queued item resolved by the operator against the translation | Yes | operator-verified |
| `reviewed` | Checked by an expert | Yes | expert-reviewed |
| `rejected` | Wrong or not extractable | No | — |

- **Who resolves the queue.** Most queue items are about direction or numbers ("is it the 7th lord in the 12th, or the 12th lord in the 7th?"). Anyone can settle those by reading the translation, so the operator can resolve them. Questions of meaning ("does this exception apply to D9 too?") are left `queued` for a reviewer, and the verse stays available as prose meanwhile.
- **What is recorded:** extractor and judge models, prompt versions, gate results and who resolved what. A gate change re-runs the gates over cached extractions.

### 5.4 Chapter maps

`sources/<edition>/chapters.yaml` (optional) declares a chapter's structure, e.g. `ch24: {structure: lord_in_bhava, order: [lord, house]}`. The operator writes it from the book's table of contents in minutes. It enables G5 and helps the extractor; without it, G5 abstains.

## 6. Topic maps without an expert

A topic map (design §11.3) lists the factors a topic depends on. Each entry now cites the passages that justify it, e.g. the 10th house for career, from the edition's chapter on house significations. Entries are drafted by the LLM from those chapters and checked by G1 and G3. The operator approves the 11 Core maps, a short task. `reviewed_by` is optional.

## 7. Polarity and contrary evidence

Polarity (supportive, adverse, mixed) used to live on cards. Factor passages get an LLM-tagged `polarity` at ingestion, marked `tagged_by: llm`. It is used only to **order** evidence and to find contrary passages (RET-6), never to decide applicability. Answers present the verse's own words.

## 8. What the expert does now

All optional; each raises a label or a target, and none blocks work:
- promote verified items to `reviewed`, and settle queued items about meaning;
- review the ontology against the edition (the operator can also do this, citing the edition, ontology rule 5);
- add notes to the golden question set;
- score readings for astrological correctness (EVAL-6, the expert part);
- choose calculation conventions (open questions B2). The provisional defaults stand otherwise.

## 9. Evaluation

| ID | What | Without an expert |
|---|---|---|
| **EVAL-11** (new) | **Extraction accuracy** on an operator-labelled sample: at least 100 factor tags across families, plus every compound card's conditions. Metrics: exact-match rate of `verified` items, **direction and number errors among verified items** (target 0), gate catch rate on seeded errors, queue rate | The labels are about what the translation literally says, so the operator can make them |
| EVAL-4 | Applicability fixtures, now generated by G6 for every verified predicate | Automatic |
| EVAL-2 | Golden questions built from the sources by the operator (question, expected passages); expert notes optional | Yes |
| EVAL-3 | Retrieval: adds factor-route recall (every passage tagged with a chart's factor keys is retrieved) and the factor-confusion fixtures | Automatic |
| EVAL-6 | Readings: coverage and faithfulness scored by the operator; astrological correctness scored by an expert when one is available, otherwise recorded as not assessed | Partly |

**Spot audit per release:** the operator checks 20 random `verified` items against their verses. Any error found becomes a seeded case for the gates.

## 10. Residual risks

| Risk | Mitigation |
|---|---|
| A shared error on a non-formulaic verse outside a structured chapter passes G2–G5; only G7 can catch it | Measured by EVAL-11 on seeded errors. The answer quotes the verse, so the reader sees the source. The spot audit samples these first |
| An LLM judge (G7) that is too lenient | Calibrated in EVAL-11: seeded wrong renderings must be rejected |
| Tagging misses a factor a verse is about (recall, not precision) | The verse is still found by semantic search; factor-route recall is an EVAL-3 metric |
| Without an expert, a school-specific misreading can be "verified" because it is literally faithful | Labels say machine- or operator-verified; the reviewer can promote, correct or reject later without rework |

## 11. Review log

Dry runs used the repository's real alias matcher and calculation engine. Verses are synthetic text in BPHS style (not quotations). The two extraction passes and the judge were simulated, because no model is available in the build container. Probes are not committed.
